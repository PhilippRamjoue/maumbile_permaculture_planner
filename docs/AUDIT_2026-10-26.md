# Product, reliability and UX audit — 26 October 2026

## Scope and conclusion

Reviewed checkout `48792ee` (frontend version 0.1.4), including the eight already-modified files in
the working tree. Those changes introduce the editor's “Back to adding” flow across Elements,
Zones, Sectors and Functions and adjust two browser tests. They appear to be the open Claude task
mentioned by the owner; its exact completion status was not independently confirmed. No existing
application source or pending changes were edited for this audit.

The current happy paths work and the automated checks are strong. The main remaining weaknesses
are protection of work across tabs and failures, handling of long-running sessions/jobs, and the
gap between what the save UI promises and what it actually saves. Address those before adding
more editor features.

<https://maumbile.ecosoul.tech>. Production TLS navigation, HTTP redirect, public pages, API
availability, frontend version and asset headers were checked. Coolify configuration, proxy
sanitization, backend image digest, backups, restore success and authenticated production workflows

## Findings requiring fixes

Priority definitions: **P1** should be handled before broader customer onboarding; **P2** should be
in the next reliability/UX release; **P3** is worthwhile follow-up. “Source-confirmed” describes a
demonstrable code path whose full customer scenario was not separately exercised in a browser.

### F01 — P1: Stale tabs silently overwrite saved work and restore deleted features

**Evidence: locally reproduced through the real API; source-confirmed in the current checkout.**

`frontend/src/features/design-editor/store.ts:93` sends every feature in the document on every
save. `backend/app/modules/planning/repository.py` updates a colliding feature whenever it belongs
to the same plan. There is no document revision/precondition. Existing conflict tests protect
against IDs owned by another plan, not against stale versions of the same plan.

Reproduction:

1. Two views start with “Original tree”.
2. A saves “Renamed in tab A”.
3. B submits its older document while making another edit. The stored name becomes “Original tree”.
4. A deletes the feature. B saves its stale copy again. The feature exists again.

This affects a single customer using two tabs or devices; it does not require collaboration.

**Fix:** add an incrementing plan/document revision checked and advanced atomically with saves.
Reject stale writes with 409/412 and preserve both the local draft and the server version for
recovery. Cover feature, layer and goal writes consistently. Merely sending changed features
reduces damage but does not solve conflicting edits to the same feature. Do not use the existing
plan timestamp as a revision without making every design write advance it.

**Acceptance:** stale renames and stale resurrection are rejected; the UI offers to reload or
retain/download the local draft instead of silently accepting destructive last-write-wins.

### F02 — P1: Share-link secrets are copied into request logs

**Evidence: reproduced with the real request middleware in an in-memory ASGI app.**

`backend/app/core/logging.py:51` and `:59` log `request.url.path`. The public endpoint embeds the
bearer secret in `/api/v1/shared/{token}/export`. A synthetic request produced a log containing
that exact token. nginx's default access logging can also retain the request URL; external proxy
logging depends on the deployed configuration.

Database hashing therefore does not keep the secret out of logs. Anyone obtaining an active
token from those logs can use its read/download access. This is an exposure path, not evidence
that any logs have been accessed improperly.

**Fix:** redact the token segment in application success/error logs and in nginx/proxy logs. Use
a route template plus a non-secret request ID for diagnostics. Avoid recording raw share URLs in
error reporting. Evaluate whether existing active links should be rotated after log access and
retention are reviewed.

**Acceptance:** success, 404 and exception tests show no raw token in any configured log sink.

### F03 — P2: Boundary changes do not follow the global save promise

**Evidence: source-confirmed in `frontend/src/features/design-editor/Workspace.tsx`.**

There are autosave hooks for features and goals (`:313`, `:321`), but none for the boundary.
The header nevertheless says “saving automatically” for a valid dirty boundary. Invalid dirty
boundaries are omitted from the header's dirty calculation (`:476`), so the header can say
“All changes saved” while the boundary has unsaved invalid changes. Boundary mutation errors
are omitted from global failure state (`:477`); their error message appears only in Boundary.

Normal rail navigation starts a valid boundary save, then changes focus immediately (`:409`).
A failure can therefore be hidden in the step just left. Switching from Boundary to Simple
uses a separate handler (`:442`) and does not initiate a boundary save at all.

**Fix:** calculate one truthful status from all three save domains. Either autosave valid boundary
changes or explicitly describe their manual save behavior. Show invalid/failed boundary state
globally, preserve a retry action in every mode, and route all mode transitions through the same
save/validation logic. Explain that a boundary belongs to the site and affects all its plans.

**Acceptance:** cover invalid boundary, failed PATCH during focus change, switching to Simple,
retry, export and navigation away. Never show “All changes saved” with an unsaved boundary.

### F04 — P2: Interrupted terrain jobs can leave the UI polling indefinitely

**Evidence: source-confirmed across terrain backend and frontend.**

`backend/app/modules/terrain/service.py:143` recognizes a stale pending/running job only on POST.
GET/view does not change or flag it. `frontend/src/entities/terrainQueries.ts:29` keeps polling
pending/running results, while `TerrainPanel.tsx:110` displays “up to a minute” without a retry
action. If the backend restarts during a job, waiting or reloading the page does not requeue it.
Even after the ten-minute stale threshold, the UI does not offer the POST needed for recovery.

**Fix:** expose a stale/interrupted state with elapsed time and a retry action. Preserve generation
guards. Durable workers can follow when usage warrants them; the UI recovery is needed now.

**Acceptance:** seed an interrupted job with an old timestamp; GET/UI exits the indefinite
spinner and a single retry schedules one new generation.

### F05 — P2: Map tiles bypass access-token refresh

**Evidence: source-confirmed.**

`frontend/src/features/map/MapView.tsx:43` adds credentials to MapLibre requests but does not use
the API client's refresh/replay path. Tiles require `CurrentUser`; access tokens expire after
15 minutes. An idle customer can pan into uncached imagery after expiry and receive 401s even
though their refresh session is valid. Another JSON request may refresh the session, but that
does not explicitly replay already-failed tiles. There is no corresponding map recovery UI.

**Fix:** coordinate session renewal for protected resource loading and reload failed map sources
after successful renewal. Provide an actionable imagery error state for session/provider failures.
Do not make private site endpoints anonymous to solve this.

**Acceptance:** with expired access and valid refresh cookies, panning still loads tiles without
reloading the page; permanent expiry offers sign-in while retaining the draft.

### F06 — P2: Multiple tabs can collide during refresh and revoke valid sessions

**Evidence: source-confirmed; the end-to-end cross-tab race was not reproduced.**

`frontend/src/shared/api/client.ts:69` deduplicates refresh only inside one JavaScript runtime.
Two tabs can submit the same old refresh cookie. `backend/app/modules/auth/service.py:131`
treats an already-revoked refresh token as replay and revokes every refresh session for the user.
Depending on timing, ordinary tab activity can therefore invalidate a successfully rotated
session or other device sessions. The database conditional update prevents double rotation but
does not coordinate the clients or distinguish benign late arrivals.

**Fix:** coordinate refresh across tabs, for example with a browser lock and session-change
notification, then recheck whether renewal is still needed after acquiring the lock. Review a
bounded server-side race policy without weakening actual replay protection.

**Acceptance:** expired-session requests in two tabs renew reliably; deliberate replay outside
the permitted policy is still rejected and tested.

### F07 — P2: Terrain percentages describe the bounding rectangle as “of site”

**Evidence: source-confirmed.**

`backend/app/modules/terrain/derive.py:142` samples the bbox window, not the site's polygon.
Fractions at `:171` use only cells with known slope. `TerrainPanel.tsx:40` labels these values
“% of site”. For triangular, concave or narrow sites, neighboring land can dominate the summary;
missing slope cells also change the denominator. This can mislead land-planning decisions even
when the overlay itself is technically rendered correctly.

**Fix:** immediately label the statistics as estimates over available data in the surrounding
bounds. For actual site statistics, mask/weight cells against the boundary, expose data coverage,
and include boundary geometry in the cache input key. Bbox-only caching is appropriate for the
current bbox computation but would be insufficient after polygon-aware statistics are added.

**Acceptance:** a steep area outside a concave site does not inflate site slope statistics;
missing-data coverage and the percentage denominator are explicit.

### F08 — P2: GeoJSON export omits the land boundary

**Evidence: local export response inspected and source-confirmed in
`backend/app/modules/export/geojson.py:18`.**

The export includes plan metadata, layers and features, but no site boundary. `PlanDocument`
already has the boundary for PNG/PDF rendering. Customers using GeoJSON as their portable copy
cannot reconstruct the outlined land from it, especially for an empty plan. Existing feature
round-trip tests do not establish that this is a complete site backup.

**Fix:** include boundary and relevant site metadata in a documented foreign member or a versioned
project export, while keeping the existing feature array compatible. Add an import/restore flow
later; describe current GeoJSON capabilities accurately in the meantime.

**Acceptance:** an empty plan's export retains its land outline; a geometry round-trip preserves
coordinates and does not import the boundary as a normal design feature.

### F09 — P2: Export can silently omit pending goals and boundary changes

**Evidence: source-confirmed at `Workspace.tsx:511`.**

`ExportMenu` receives only feature/layer `dirty`, excluding pending goals, boundary changes and
the broader saving state. All downloads use server-saved content. Exporting while a goal save
is pending or after adjusting the boundary can therefore produce an older document without the
menu's unsaved warning. The current warning also allows downloading older feature content.

**Fix:** give export the complete save state. Offer “Save and download” and handle failed or
invalid content explicitly. If downloading the last saved version remains available, label it.

**Acceptance:** delayed goal saves and failed boundary saves cannot produce an apparently
up-to-date export without an explicit customer choice.

### F10 — P2: Public-resource limits and proxy trust need hardening

**Evidence: repository defaults and an in-memory proxy test; production exposure is conditional.**

Registration performs Argon2 hashing without the login limiter (`auth/router.py:61`). Export
rendering and terrain jobs also have no global concurrency budget; the terrain extent limit is
per job. A public instance can therefore spend substantial CPU/memory on concurrent requests.
No load attack was performed.

Additionally, nginx appends incoming `X-Forwarded-For`, and Compose configures Uvicorn to trust
all forwarding addresses. With `X-Forwarded-For: supplied-address, actual-proxy-address`, the
installed middleware selected the supplied first address. The per-email login limit still
applies, but IP throttling can be bypassed if the outer proxy preserves user-supplied values.
The in-memory limiter also retains distinct keys indefinitely.

**Fix:** establish and test a trusted proxy chain at the public edge; sanitize forwarded headers
there and trust only known proxies downstream. Add registration throttling, bounded expensive
job concurrency and limiter-key cleanup. Keep deployment-specific claims conditional until
Coolify's actual proxy behavior is checked.

**Acceptance:** a forged forwarding header cannot change the derived public client identity;
bounded synthetic concurrency is rejected/queued predictably without harming normal sessions.

### F11 — P2: Site setup loses its draft when leaving or reloading

**Evidence: source-confirmed in `frontend/src/features/site-setup/SiteSetupPage.tsx:17`.**

The setup store is reset on mount and unmount. Unlike the design workspace, setup has no unsaved
navigation guard. A customer who enters many corners and accidentally follows a link loses the
work. This is especially painful on phones and unreliable connections.

**Fix:** retain a recoverable setup draft with a clear “Resume / Start over” choice, scoped to the
account and cleared on sign-out. A navigation warning is a useful smaller first improvement.
Treat stored location data deliberately; do not silently persist it across unrelated accounts.

**Acceptance:** accidental navigation/reload preserves the draft or warns first; a different
account cannot see the previous customer's draft.

### F12 — P2: Site management and account recovery are missing from the customer UI

**Evidence: frontend routes/components and auth API inspected.**

Plans can be renamed and deleted. Sites have update/delete backend support, but the dashboard
and site-map UI offer neither site rename nor deletion. A mistaken site remains in the customer's
list. This also conflicts with the privacy copy saying sites can be deleted in the app.
Password recovery/change is absent; forgetting a password has no self-service resolution.

**Fix:** add a clearly scoped site-settings action, distinguishing deletion of an entire site
and all its plans from deletion of one plan. Add a tested account recovery flow and a private
support contact. Update product copy to match capabilities that actually exist. This is a product
gap, not evidence of an authentication bypass or account takeover.

### F13 — P3: Lists silently stop at 100 records

**Evidence: `frontend/src/entities/siteQueries.ts:15` and design-editor `api.ts:22`.**

Both list calls request the first 100 records and the views do not expose pagination despite
receiving paginated responses. Older sites/plans become inaccessible through normal browsing
once that threshold is exceeded.

**Fix:** add “Load more” or pagination using total/offset, with search when needed.
Test with 101 records and stable ordering. Low urgency for small accounts, but a real limit.

## Performance and deployment improvements

These are source-based opportunities, not measured production bottlenecks.

1. **Reduce write amplification.** `persistDesign` sends the whole document and PATCHes every
   layer even when only one feature name changed (`frontend/src/features/design-editor/api.ts:64`).
   With five default layers that is six API writes per autosave. Patch only changed layers and
   features, retaining atomic deletions and the persisted-ID recovery behavior. Pair this with
   F01's revision check. Measure requests, bytes and save latency on 100/500/1,000-feature plans.
2. **Release DB connections before slow provider I/O.** Auth and site lookups share the request
   session; the imagery path then awaits an upstream HTTP request without ending its read
   transaction. Default Esri tiles bypass the database cache. Slow concurrent tiles can occupy
   database connections also needed by saves/readiness checks. Restructure the read scope while
   preserving ownership checks; verify with bounded slow-upstream tests before tuning pool sizes.
3. **Reduce full-document work per edit.** `store.ts` serializes and clones the whole document and
   keeps up to 100 document snapshots. `useEditorMap.ts` recreates design sources/layers on document
   changes. Benchmark ordinary typing and dragging on realistic large plans, especially phones.
   Prefer source `setData`/incremental updates and compact undo patches where measurement supports it.
4. **Improve cold loading.** The build reports MapView at about **1,065 kB / 293 kB gzip**, plus a
   separate **517 kB worker** (raw output size). Existing lazy loading and nginx gzip help. Add
   immutable caching for hashed assets and an intentional index revalidation policy, then measure
   first-map time on a slow connection. Do not simply increase the warning threshold.
5. **Make releases a tested pair.** `release.yml` gates publishing on the changelog check, not
   lint/tests. Its matrix publishes frontend/backend independently, while Coolify defaults to
   mutable `latest` with `pull_policy: always`. A failed/partial publication or redeploy during
   publication can mix versions. Gate releases on reusable verification, deploy immutable versions
   after both images succeed, and record deployed image digests. Pinning a shared version is useful
   immediately; migration rollback still needs a backup/restore strategy.
6. **Plan for updates in already-open browsers.** nginx's generic SPA fallback returns HTML
   for a missing hashed JS asset; the production check confirmed **200 text/html** for a missing
   `/assets/*.js` request. Serve missing assets as 404 and add a clear
   “A new version is available—save, then reload” recovery for lazy-import failures. Test an open
   tab across a deployment, not just a fresh page load.
7. **Bound retained state.** Add maintenance for expired refresh tokens and expired imagery-cache
   rows; TTL filtering alone does not delete old rows. Preserve the documented soft-delete policy
   and avoid treating it as permanent erasure. Observe actual DB growth before adding infrastructure.

## UX improvements, in recommended order

### 1. Make placing the first item unmistakable

The simple editor opens with Tree selected in the palette but the Select/edit tool active.
The helper says “One click places…” and the empty list says choose a palette item and click the
map. Choosing a *different* palette value starts placement, but a customer happy with the default
Tree can click the map and get no new tree.

Use one prominent action such as **“Place tree on map”**, updating its label with the chosen item.
While armed, say **“Tap the map to place your tree”** and show a clear cancel action/cursor.
After placement, retain the new “Back to adding” pattern and a clear **“Place another tree”** action.
This complements Claude's current panel work rather than replacing it.

### 2. Keep controls close to the map on phones

The narrow browser inspection showed the header, save explanation, mode switch and six-step rail
taking most of the initial view. The map comes before the controls, so choosing a tool or editing
a selected item can require repeated scrolling away from the map.

Keep the map visible with a compact toolbar and an expandable bottom panel for the active task.
Collapse repeated explanations after first use, shorten the rail to the current/next step with an
“All steps” control, and make touch targets comfortably sized. Preserve keyboard and screen-reader
access. Validate at 360/390 px, landscape, 200% zoom and with the software keyboard open.

### 3. Help customers locate land before outlining it

Country selection and coordinates work, but a country-wide satellite view gives non-experts little
help finding their farm. Add a “Find my land” entry with an address/place search, a single Google
Maps coordinate paste and an optional location button. Ask for geolocation only after the customer
chooses it; keep the manual method. Explain coordinate order with a preview rather than requiring
geospatial knowledge. Any search provider needs an explicit privacy/data-source choice.

### 4. Offer recovery rather than only discard

The unsaved-design dialog currently offers “Keep editing” and “Discard changes and leave”. Add
**“Save and leave”**, retaining the draft on failure. A small local recovery snapshot for an
unsaved design would help after crashes or lost connections; scope and clear it by account.
Distinguish “Saved on this device” from “Saved to your account” if local recovery is introduced.

### 5. Make exports useful without specialist knowledge

Explain PNG/PDF as a printable plan and GeoJSON as editable geographic data. State before download
that rendered exports omit aerial imagery. Offer “Save and download”, a preview and useful print
options only where needed. Explain that read-only share links expose download access, including
the full GeoJSON feature data; hiding a layer is not a privacy boundary.

### 6. Improve navigation and portfolio management

Add site cards with small previews, site settings and a “Continue last plan” action. Provide
“Duplicate plan” for comparing alternatives without rebuilding a design. Keep deletion specific
and recoverable where possible. Show a useful empty plan-list state before the create form.

### 7. Make accessibility and poor connections part of acceptance

Provide actionable map/provider errors, a retry control and visible connection/save status.
Check focus placement and trapping for the unsaved dialog, keyboard-only plan management, contrast
in both color schemes, touch behavior, and announcements that do not repeat excessively during
editing. Map interaction should have usable form alternatives where practical. The current seven
browser tests use one desktop viewport and stub imagery; they do not establish mobile usability,
accessibility conformance or real tile-provider resilience.
